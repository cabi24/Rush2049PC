# r1: the game image from 0x80086A50 to 0x8009DC50

The first 94 KB of the game image's code: 239 functions. This page is a map of them for a programmer new to the game:
what they do, which original source files they come from, the data they share, how they call each other, what only
the N64 has, and what is still unsure. The names are the ones `tools/port/names/r1.tsv` proposes (wave 1 of
[PCONLY.md](../port/PCONLY.md)); where a function is better known by its old name, the old name follows in brackets
the first time. Every MAT3 name was matched against the GameCube decomp's C (`SFRush2049-mat3-decomp`,
`decomp/src/GameSource/src`): the same constants, callees, fields and control flow.

## 1. What this part of the game does

Five things, roughly in this order in memory:

1. **The N64 platform layer for 2D drawing and the serial bus** (0x80086A50-0x8008AD04): the blitter that draws
   every 2D sprite and rectangle into its own display list (`blit_dl`), the SI lock that serialises the controllers,
   paks and rumble motors, the Rumble Pak thread, and two sound threads (the per-retrace audio thread and the
   sample-DMA thread of the sound library).
2. **The scene-object system and the car visuals** (0x8008AD04-0x80094888): the "zoid" object tree
   (`ObjInstanceList`, MAT3 zoid.c / mbox.c), its flat polygons (zoidpoly.c), the vector maths (fmath.c, atan.c),
   and the per-car animators of visuals.c (sparks, brake lights, arrow, shadow, tires, wings, the explosion and its
   ring, the car body and its rocket flame) with the smoke and water spray of smoke.c.
3. **Small services** (0x80094888-0x80095198): the save code's file hooks, the high-score table clean-up, the blit
   instance list (zoidblit.c, UpdateBlit, Hidden), comparators and libc copies.
4. **The sound stack** (0x80095198-0x80099B30, with the heap and the waves among it): the game-side sound manager
   (audiomgr.c: fx tags, sequences, 3D emitters, priorities), the sound server (audiosfx.c: instances and a command
   queue), the N64 forms of MAT3's PS2 audio layer (audiosysps2/audiosfxps2/audiosongps2.c), the heap (memsys.c),
   the asset loader (waves.c, mb_wad.c) and a binary tree (bstree.c).
5. **The scene draw** (0x80099B30-0x8009DC50): the per-node model draw of the N64 renderer (LOD, textures, palettes,
   lookats) and the fixed-point matrix builders, with farcsine. MAT3 has no counterpart: the GameCube draws through
   `NGC/ngcZoid.c`.

## 2. Why the module boundaries are blurred

The retail game image is one object: the whole game was compiled as one IDO `-O3` program (ucode linked, then
`umerge`, `uopt`; [COMPILER_SETTINGS.md](../COMPILER_SETTINGS.md)). `umerge` inlines statics and reorders
procedures, so the image is not laid out file by file as the GameCube's is. What survives:

- **A file's functions come out in roughly reverse source order.** bstree.c is the clearest case: `WalkBSTInternal`,
  `WalkBST`, `InsertBSTEInternal`, `InsertBSTE`, then a stub (InitBST) is MAT3's order backwards. audiosfx.c's setters
  run `AudioSetMono`, `AudioSetEffectPitch`, `...FBPan`, `...LRPan`, `...Volume`, `AudioPlayEffect`: MAT3's order
  backwards again.
- **Callees are placed near their first caller.** zoidpoly.c's `ZOID_HidePoly` sits right before `AnimateArrow`,
  ll.c's `InsertLLE`/`RemoveLLE` right after the audiomgr functions that use them, `ZOID_UpdatePoly` before the
  arrow and the shadow.
- **Inlined statics leave an 8-byte `jr ra; nop` stub** where they would have been ("deleted procedures"). Nothing
  calls them; the map names them `dead_stub_*` or after the static when the position says which one.

So the "modules" below are runs of addresses, not files.

## 3. The main data structures

**The blit state** (MAT3 blit_pc.c's globals, all kept): `blitAttribute` (bit 1 alpha compare, 4/8 flip in x/y, 0x10
use `blitZDist`, 0x20 translucent with `blitPrimColor`'s alpha, 0x4000 fill-rectangle combiner, 0x8000 interlaced
halves), the clip window `blitXmin/Ymin/Xmax/Ymax`, `blitMode` (the RDP mode last set, -1 none), `blitLUT` (TLUT mode
last set), `blitColors` (the colour/palette address last loaded) and two N64-only caches, `blit_cache_image` and
`blit_cache_tile`, that skip reloading a texture already in TMEM. Everything goes into `blit_dl`, a cursor into a
double-buffered display list that `BlitInit` swaps each frame.

**The scene objects** `ObjInstanceList[600]` (0x44 bytes on the N64; [POINTERS.md](../port/POINTERS.md) 9.2): `flags`
(+0; 0x80000000 hidden, bits 8-11 the cameras it is hidden from, the rest the creation flags such as 0x40000,
0x42000, 0x52000), `mat` (+8, a
`tUVMatrix *`: 3x3 rotation then position), `scale`, `w`, `index` (+0x14, the model def `(wave << 10) | object`,
0xFFFF free), `child` (+0x16) and `next` (+0x18) links (-1 none), a light pointer, `texture[4]` (+0x20, one per LOD),
the tile rectangles, a palette, `color` and `envcolor` (+0x3C/+0x40). `ObjHead` is the first top-level node,
`gNumObjects`/`gMaxObjects` the high-water marks. `ZOID_AddObject` takes the first free node and links it with
`ZOID_InsertObject`; `RemoveObjectTree` frees a node (and its children and/or siblings). The `MBOX_*` functions are
the friendly face: `MBOX_NewObject`, `MBOX_HideObject`/`MBOX_ShowObject` (mode 0 one node, 1 one camera mask, 2 and
3 the subtree), `MBOX_FindObject_WORK` (a model def by name, by bsearch over each loaded WAD's OBHD records with
`objcmp`).

**Flat polygons** `PolyInstanceList[200]` (`tPoly`, 0x58 bytes on the N64): `nverts` (0 free), `flags` (0x8000
hidden, 0x400 textured, 0x4000 screen-space), `texidx`, and four vertices in the N64 `Vtx` layout. The arrow, the
shadow and the skid marks are polys; `ZOID_UpdatePoly` writes their corners and texture coordinates.

**Car visuals** (`tVisual`, 0x18 bytes on the N64, 0x20 on the PC; [CARS.md](../port/CARS.md) 3): `next`, `index`,
`objnum`, `slot`, `data`, `timeStamp`, `func`. Each car record holds 21 of them (+0x110); each frame the game calls
`func(v, op)` for each (op 0 removes). The environment visuals are a pool: `GrabEnvEntry` pops `gFreeVis`,
`AddToEnvList` pushes it on `gEnvList`, `ReleaseEnviron` gives it back; `gEnvCount`/`gEnvCountMax` count them.
The explosion uses `gBlastObjs[6]` (four sphere objects and a glow, each on a matrix inside the record) and
`gBlastRingObjs[6]`; the smoke uses the pool `gSmokeList` and the per-car latch word `gCarSmokeDir` (bits 0x1-0x8
tire puffs, 0x10-0x80 and 0x80000 smoke, 0x100-0x800 water, 0x1000-0x8000 the wing trails).

**The waves** (MAT3 waves.c): every asset is a "wave", file *n* of the cartridge's table (`wave_rom_offsets`,
`gWaveSizes`, `wave_storage_kinds`: raw, LZSS or DEFLATE). `gWaveInstance[64]` (0x14 bytes: loaded, ready, locked,
model, mirrored, handle, wave, size, ptr) records the loaded ones. A model wave is a WAD (MAT3 mb_wad.c: a TOC of
`{tag, address, length}` entries) that `SetupWaveModel` relocates in place: its display lists (`relocate_model_dl`,
which also rewrites the LOD markers for the player count), its texture loads (`relocate_texture_loads`), and the
model, texture and palette tables `gRomObjDefPtrs`, `gTexDefPtrs`, `gPalDefPtrs`. [ASSETS.md](../port/ASSETS.md)
has the formats.

**The heap** (MAT3 memsys.c): `gMainHeap` (`tHeap`: next heap, chunks, last chunk, endRam, the handle blocks) of
`tMemoryChunk` headers (32 bytes: magic, next, prev, size, master, used, internal, locked). Handles
(`AllocateHandleHeap`) are slots in master blocks, so a handle's block can move. Every API call takes the heap lock
(`heap_lock`, an N64 message queue).

**The sound stack**, three layers:

1. *The sound manager* (MAT3 audiomgr.c), what the game calls: fx tags `gFxTags` (handles are
   `(generation << gTagShift) | index`, checked by `ConvertTag`), on the lists `gFreeFxTags`, `gInterruptedFxTags`
   and the playing list; messages `audiomgr_gCmds[128]` (MAT3 `gCmds`) from `GetCmd`; 3D emitters and listeners
   (`gActiveEmitters`, `gFreeEmitters`, `gActiveListeners`); sequences (`gActiveSequences`, `gFreeSequences`). On the
   N64 the game posts each message to `audio_command_queue` under `audio_lock_queue`, and `audio_manager_thread_entry` runs
   them; each retrace it runs `PeriodicMaintenance` (emitters, sequences, then the priority pass: the tags sorted in
   a `tOrderedList` by `WeightedPriority`, `UpdateFx` keeps the first `gMaxSfx * 0.75` playing).
2. *The sound server* (MAT3 audiosfx.c): instances `gSfxInstances` (24 bytes on the N64: used, started, stop,
   stopped, stopAll, fail, index, soundId, the voice handle) and commands on `gFreeQ`/`gCmdQ`; `AudioPlayEffect` and
   the setters queue commands with `SendCmd`, and `AudioSfxServer` runs them each retrace against the free voices
   (`gNumChannels`).
3. *The sound library* (MusyX-style, in the boot code): voices, songs (`AudioSongPlay`, `song_handle`,
   `song_groups`), the sample DMA list (`sample_dma_list`, served by `sample_dma_thread_entry`) and the clock
   `gAudioSeconds` that `audio_retrace_thread_entry` advances.

**The paks and rumble**: `gPaks[4]` (772 bytes each on the N64; MAT3 `gPaks`): inserted (+1), the rumble byte (+6,
`PS_PakRumble`), the OSPfs, the error, the motor fields (+0x7C motor on, +0x7D requested level, +0x7E level, +0x80
phase) and 16 file slots. `rumble_thread_entry` ramps level toward the request and drives the motor through
`rumble_duty_masks`; `gRumble` switches it off.

## 4. How the functions call each other

**2D.** The HUD and the menus (other ranges) call `BlitScissor`, `BlitXLU`, `BlitZDist`, `BlitColors`, `BlitDraw`,
`BlitRect`; `blit_load_texture` loads the image and picks a mode through `blit_set_mode`; `BlitSetAttribute` /
`BlitClearAttribute` toggle state. The blit instance list (`gBlitInstanceList`, MAT3 zoidblit.c) is filled by
`UpdateBlit` (`ZOID_UpdateBlit`, `ZOID_CropBlit`, `ZOID_SetBlitData`, `ZOID_FlipBlit`, `ZOID_TextBlit`), and blit
animators such as `Hidden`, `animControllerDimInternal` and `anim_show_on_high_score` call it when they change a blit.

**Car visuals.** StartCar and its helpers (next range) set each visual's `func`; every frame the visuals pass calls
them: `AnimateFrame` (the body: colours by `GetCarsIRColor`'s inlined N64 form, `SetFrameColor`, `SetSheenColor`, the
hulk by `PickCar`, the mine cheat; it calls `AnimateRocketFlame` for body type 2), `AnimateTire` (spring, spin,
`CreateYPRMatrix`, `ZOID_UpdateObject`), `AnimateShadow` (a poly from the tire positions), `AnimateArrow`,
`AnimateBrakeLights`, the five spark animators through `HandleASpark` (`PositionObject` → `LookInDir`),
`AnimateWing` (with `InitWingSmoke` and `StartSmoke` types 6/7) and `AnimateWingFlame`. All of them show or hide
through `CheckVisibleAll`/`CheckVisible` → `MBOX_ShowObject`/`MBOX_HideObject`. A crash starts `AnimateBlast` (the
explosion frames via `ZOID_SetObjectDef`), which starts `StartNewBlast` (`AnimateNewBlast`) and the ring
(`AnimateNewBlastRing`); `StartNewBlast` also calls `StartSmoke(slot, 5)`. `StartSmoke` and `StartWater` take puffs
from `gSmokeList` (`GetStatLLE`) and make objects with `MBOX_NewObject`.

**Sound.** Game code → `AudPlayEffect` (`audio_lock`, `GetCmd`, `GetFxTag`, post, `audio_unlock`),
`AudChangeEffectVol`/`AudChangeEffectPitch` (→ `AudChangeEffect`), `AudStopEffect` → `audio_command_queue` →
`audio_manager_thread_entry` → the command cases → `AudioPlayEffect`/`AudioStopEffect`/the setters (audiosfx) → `SendCmd`.
Each retrace: scheduler → `audio_manager_thread_entry` → `PeriodicMaintenance` → `ProcessEmitters`
(`normalize_vector_or_x`, `clamp_gain`, `AudChangeEffect`), `ProcessSequences` (`AudPlayEffect`, `FreeSequence`),
the priority pass (`ClearBST`, `InsertBSTE`, `WalkBST` → `UpdateFx`, ordered by `OrderFx`) and `AudioSfxServer`
(→ `AudioPlayEffectInternal` and the sound library). Separately, `audio_retrace_thread_entry` runs the sound library's callback
and advances `gAudioSeconds`, which `AudioTimeout`/`AudioTimeoutPerc`/`GetAudioTime` read.

**Assets.** `LoadWave` (`FindWaveInstanceInternal`, `MirrorWaveInstance` for a loaded one; else a heap block from
`AllocateMemoryHeap`/`AllocateHandleHeap`, `GetPtrSize`, `SetWaveInstanceModel`) → `ReadWave` now, or the
background loader through `bg_load_request_queue` → `wave_rom_read` / LZSS / inflate → `SetupWaveModel`
(`MBSetupWad`, `MBGetFromWad`, `MBOffsetWad`, `relocate_model_dl`, `relocate_texture_loads`,
`mirror_vertex_texcoords`). `UnloadWaveInstance` frees one (`DeallocateMemory` → `DeallocateMemoryInternal` →
`FindHeap`, `FindChunk`, `FillFreeMem`).

**Scene draw.** The per-view set-up and the scene walk (next range) call `zoid_draw_object` for each node:
LOD by `node_eye_distance`, `lookat_reflect_fill` for reflective parts, `zoid_load_texture` → `zoid_load_palette`,
then the node's display list; the walk builds each node's matrix with `build_node_matrix` (or the far-scenery and
four-row forms). `farcsine` is the model draw's arc cosine and arc sine kernel; `fasin` (its arc sine) is also used
by the resurrect camera.

## 5. N64-only: no MAT3 counterpart

- The blitter's RDP side: `blit_set_mode`, `blit_load_texture`, `blit_mask_bits`, the RDP parts of the attribute
  setters, `BlitZDist`'s SETPRIMDEPTH, `blit_dl`.
- The SI lock and the Rumble Pak: `si_lock*`, `si_unlock*`, `rumble_thread_entry`, `rumble_duty_masks`, the motor fields of
  `gPaks`, `pak_removed`.
- The threads and their queues: `audio_retrace_thread_entry`, `audio_prenmi` (pre-NMI), `sample_dma_thread_entry`,
  `sample_dma_next` (PI DMA), `audio_manager_thread_entry`, `audio_lock`/`audio_unlock`, `heap_lock`/`heap_unlock` (MAT3's
  semaphores are empty), `wave_rom_read` (PI DMA from the cartridge).
- The display-list walkers of the asset loader: `relocate_model_dl` (24-bit addresses, segments, LOD markers),
  `relocate_texture_loads`, `display_list_traverse`, `flip_triangle_winding`, `mirror_vertex_texcoords`.
- The scene draw: `zoid_draw_object`, `zoid_load_texture`, `zoid_load_palette`, `lookat_reflect_fill` (a cut-down
  libultra guLookAtReflectF), the fixed-point `build_*node_matrix*`. MAT3 renders through NGC/ngcZoid.c instead.
- The N64 forms of MAT3's PS2 audio layer: `AudioSetMasterVolume`, `AudioSongPlay`/`AudioSongStop`,
  `AudioPlayEffectInternal`, the song data (`musyx_project`, `musyx_pool`, `musyx_sdir`, `musyx_samples`).
- `expansion_pak_present`: with the Expansion Pak (or in an arena) the explosion gets its glow and fire smoke,
  and races load extra waves.

## 6. What is not identified, or only likely

- **The empty stubs**: `audiomgr_stub`, `stub_after_MovePlayerFile`,
  `stub_before_RemovePlayerScores`, `stub_after_AudioSetEffectPitch`, `stub_before_AudioStopEffect`,
  `stub_before_FillFreeMem`, the seven `audiosongps2_stub_*`, `stub_before_AudioSfxServer`,
  `stub_after_ClearBST`, `stub_before_AnimateRocketFlame` (probably GetCarsIRColor's). Each is a static IDO
  inlined; which one is not recoverable from position alone. `InitBST` and `FreeSfxInstance` are named from the
  reverse-order rule and are likely, not sure.
- **Stub bodies the decomp supplied**: `GetSfxInstance`, `NewCmd`, `sfx_cmd_list_add`, `NewWaveInstance`,
  `FindWaveInstance`, `clamp_gain`, `si_unlock_inline` and `DeallocateMemory_stub` are empty in retail (the code is inlined
  into their callers); the C gives them bodies so the callers read well. `DeallocateMemory_stub` has `DeallocateMemory`'s
  body and should become `DeallocateMemory`.
- `BlitColors` (likely): the N64 form takes four arguments and loads palettes; the role (the blit's colour source,
  cached in `blitColors`) is MAT3's.
- `animControllerDimInternal` (likely): MAT3 has only a stripped placeholder of that name; the N64 function is the
  controller-warning blit's animator, which fits.
- Data named from use only: `scheduler_audio_task`, `start_water_sentinel`, `tire_blur_texture`, the tail-light colour blocks,
  `gFogIntensity`, `font_image_format`, `zoid_branch_slot`, the `snd_*` blocks, `gPaks`/`gNumPlayers`/`gPlayers`/
  `gGoodFrameRate`/`gWheelTextures`/`gBackwards`/`gNumWindows` (MAT3 names by role; the N64 records differ in size).

## 7. Oddities found while naming

- **`ZOID_ChangeTexture` with lod < 0** sets flag 0x8000 on `lod[lod]`, index -1, in its all-LODs loop instead of
  `lod[i]`: it writes the u16 before the LOD array (the model def's header) and leaves the LODs unmarked. MAT3 has the
  same slip, so it is the original's; the N64 game passes 0 where we saw it (HandleASpark), so it may never fire.
- **`AudioSfxServer`'s stopped-channel history** (`gStoppedChannels`): as decompiled the shift loop copies each
  word onto itself (and reads `gStoppedChannels`, the word before the array), so the history never moves; only the newest
  entry is used. Worth checking against the disassembly; harmless either way.
- **`GetFxTag`** and **`NewCmd`** take the head of their free list without checking it (MAT3 too): an empty list
  is a null dereference on the N64. The PC counts and refuses those cases ([AUDIO.md](../port/AUDIO.md)).
- **`MBOX_ShowObject`** has an unreachable second `mode == 0` branch (the original's), and **`ReleaseEnviron`**
  updates `gEnvCountMax` after a decrement (harmless).
- `audio_retrace_thread_entry` calls the callback with itself as the argument (a decomp shaping device; see its header).
- `audiomgr_thread.c` has a static `_SendCmd` (the decomp's name for posting to `audio_command_queue`) that is not MAT3's
  `_SendCmd` (audiosfx.c, `SendCmd` before this map, now `SendCmd`): wave 2 renames that static
  ([NAMING.md](NAMING.md)).
