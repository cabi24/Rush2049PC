# r5: the end of the game image (0x800E847C to 0x8010FD7C)

This page maps the last 238 functions of the game image, the decompressed code at 0x80086A50 that holds most of the
game (the overlays at 0x8038xxxx and the boot code are other areas). Names here are the ones in
[tools/port/names/r5.tsv](../../tools/port/names/r5.tsv), which also names every datum these functions use, the
struct fields they read by raw offset and the files named after addresses. The N64 address of a function is given
where it helps you find it in `layout/game.json` or `asm/us/blob/symbols.json`; nothing else should need it.

The original names come from the MAT3 decomp (the GameCube build of the same game, with its debug information): a
name is the original when the function or datum was shown to be the same (same strings, constants, callees, loop
shapes, field offsets); MAT3's file names (`camera.c`, `hud.c`) are the original source files.

## 1. What this part of the game does

Almost every layer of the game has some code here:

- **The game's main loop and race flow** (`game.c`): `GameLoop` runs once per frame and dispatches on the game
  state; `UpdateGame` is the race state machine (pole positions, `PrePlay` loading the track and cars, the
  countdown, `PlayGame` each racing frame, `EndGame`); the attract-mode race (`demo.c`); the front-end dispatch
  (`updateFrontEnd`).
- **Start-up and the N64 frame pipeline**: `InitSystem` (`Init.c`), the scheduler loop of the main thread
  (`process_scheduler_message`), `StartGraphics` and `EndGraphics`, which open and close each frame's display list
  and hand the RSP task to the scheduler.
- **The car camera** (`camera.c`): the per-window camera modes (in-car, chase, the attract and finish cameras, the
  steady and max-path cameras of the attract race) and the per-frame `CheckCameraView`.
- **The car model driver** (`mdrive.c`): `Update_MDrive`, `update_game_data` (copies the model thread's results into
  the car records), `init_cars`, `munge_gLink_data` (who drives which car), plus the max-path AI's
  `FindMaxpathIntervals` (`maxpath.c`).
- **Text** (`HAL_text.c`): the font state and the text display list.
- **The HUD** (`hud.c`): every HUD element is a *blit* whose animation function runs each frame: speedometer,
  tachometer, gear, odometer, timers, place, lap counter, wrong-way, radar, track map, flag, result panes.
- **Records, unlocks and the end of a race** (`gamerecords.c`, `circuit.c`, `highscorescr.c`, `gameoverscr.c`):
  recording a finished race into the profiles, the unlock rules, the circuit (championship) state and password,
  the high-score and game-over screens.
- **The resident animators of the option screens** (`audioscr.c`, `controlscr.c`, `optionscr.c`, `pausescr.c`,
  `videoscr.c`): the screens' logic lives in overlay A or elsewhere in the image, but their blit animation
  functions are here, because the pause menu uses them during a race, when the front-end overlay is not loaded.
- **Track objects** (`targets.c`): collision tests and start/animate functions for cones, mines, weapon icons,
  coins, fences, windows, cacti, flags and knock-downs.
- **The MusyX sound library's services** (N64 only): eight functions the library calls through a table.

## 2. How the image is laid out

The N64 game image was compiled by IDO with `-O3` as one interprocedural unit (the group headers in `src/blob`
call it the whole-program unit), and that shapes the address order:

- **Callees come first.** Inside a call tree a function comes right after the functions it calls, whichever file
  they were in. So the image is not one source file after another: `camera.c`'s functions come right before
  `Update_MDrive`, which calls them, and `gamerecords.c`, `circuit.c` and `highscorescr.c` are interleaved in one
  run that ends with `updateHighScoreScreen`.
- **Inlined statics leave stubs.** A static function that IDO inlined at every call site leaves an 8-byte empty
  function (`jr ra; nop`) where it would have been. There are 13 such stubs in this area, named `X_stub` after the
  function they stood for when the position tells it (`UpdateDroneObjects_stub`, `ControlScores_stub`) or after
  where they sit when it doesn't (`hud_inlined_stub`). Nothing calls them and they can be deleted. Where the tree's
  C gives such a stub the inlined body (so the PC build can call it), it has the plain MAT3 name instead
  (`EndGame`, `initDemoGame`, `InitGfx`, `find_sequence`).
- **Functions nothing in the image calls**, the ones reached from the overlays or through function pointers
  (blit animators, target functions, the MusyX services), come grouped by original file, the files in
  alphabetical order: descending from `fmath.c` to `audio.c` (0x800FD724..0x800FECA3), then ascending from
  `audioscr.c` to `videoscr.c` (0x800FECA4..0x8010FBB3).
- **Data** (`.data` from 0x8010FD7C) is grouped per unit, not in code order; a screen's statics sit together even
  when its functions are split between the overlay and this area.

The loader's symbol table (`asm/us/blob/symbols.json`) has 132 names in this range that start no function: labels
at round addresses inside functions (`collision_mesh_load` at 0x800E9000, `anim_play`, `model_load`,
`net_lobby_update`, `session_host` ...), the case labels of `UpdateGame` that `docs/memory_map.md`'s game-state
table points at (`state_init_handler` ...), and second names at function starts (`particle_update` at
`animCountdownTimer`, `update_active_objects` at `DrawBlits`, `state_transition` at `UpdateGame`). None of them is
a function; 39 of them are still declared in the context preambles of the C files (prototypes only), the rest are
used nowhere. They should be dropped, not renamed.

## 4. Main data structures

**The car and model records.** `pc_cars[]` (MAT3 `tCarData`, the N64 0x3B8 bytes; see
[docs/port/CARS.md](../port/CARS.md)) and `pc_models[]` (MAT3 `tModelData`, 0x808 bytes, the same layout as MAT3).
Up to the visuals the car record matches MAT3 (`dr_pos` +0x8, `dr_vel` +0x14, `dr_uvs` +0x2C, `place` +0xEE,
`place_locked` +0xEF, `mileage` +0x108); after them (N64 +0x308) every field sits 0x18 lower than on the GameCube:
`mpctl` +0x314, `crash_state` +0x358, `camera`/`view`/`saveview` +0x35C..+0x35E, the input record pointer
`player` +0x380, `battle` +0x384 (its first byte is the weapon type). The map's `field` rows name the offsets this
area reads raw.

**The cameras.** `gCamera[4]` (MAT3 `anon_mat_n64_98`, 0x98 each): the camera matrix, its N64 copy (`n64`, four
rotation terms negated for the renderer), the follow camera `fcam`, `view2spring`, and `slot`, the car the window
follows. `camera.c`'s per-camera statics (`elasticity`, `elastic_factor`, `rear_y`, `rear_z`, `lastSwitch`,
`camera_nextSwitch`, `cur_acc`, ...) are `[4]` arrays indexed by the camera, which the local views in the C call `slot`.

**Text.** `HAL_text.c`'s statics (`gFontColor`, `gTrans`, `gLeading`, `gSpacing`, `gFontAttribute`, `gFontXpos`,
`gFontYpos`, the glyph buffer `gBuffer`, `gFontHeader`, `gFontLetters`) and the text bank `gText` (MAT3
`anon_numSingle_single_28`: `single[]`, `tab[]`, `taba[]`; the loader called it `gText`). On the N64 the
text "semaphore" is a real message queue every text call takes and gives back (`text_lock_queue`).

**Blits** (`blit.c`). A blit is a 2-D sprite or a pure draw callback: texture name and index, x/y/width/height, a
source window, alpha, `animID`, `animFunc`. `NewMultiBlit` builds a chain from a `tBlitDef[]` table (a
*multiblit*); `DrawBlits` runs every live blit's `animFunc` each frame and removes the blit when it returns 0. Most
of this area's HUD and menu functions are such animators: they take the blit, read `animID` (which player, which
digit), show or hide it (`Hidden`), move it, rename its texture (`RenameBlit`, `SelectBlit`) or draw text, and
return 1. `gBlitInstanceList` (200 x 32 bytes; the loader called it `gBlitInstanceList`) holds the instances the renderer
draws, indexed by a blit's `BLIdx`.

**HUD tables** (`hud.c`). Screen positions per window count and player, `s32[4][4][2]` ({x, y} for 1..4 windows
and player 0..3): `speedPos`, `tachPos`, `odometerPos`, `placePos`, `lapCountPos`, `lapTimePos`, `wrongWayPos`
(also the result panes), `radarPos`, `bonesPos`, and `elapsedTimerPos`, `hud_mapPos` per window count only; the
show options `gShowSpeed`, `gShowTach`, `gShowOdometer`, `gShowElapsed`, `gShowPlace`, `gShowWrongWay`,
`gShowRadar`, `gShowTrackMap`; per-window state `wrongWayTime`, `TrackTimeStr`, `resultPane[5]`; the track map's
`kMapSize`, `gPathMin`/`gPathMax` (the track's bounding box) and `dot_order_list` (the cars' dot order, humans
last); `radarWidth`/`radarHeight`, published by `animRadar` for `animRadarBlip`.

**Records** (`gamerecords.c`, `circuit.c`). Totals over all profiles (`gTotalRaceStats`, `gTotalStuntStats`,
`gTotalBattleStats`, `gTotalObstacleStats`, `gTotalCircuitStats`), who holds each top score (`gTotalNames`, a
profile, one of 20 temporary names, or -1), the unlock tables `gUnlocked{Tracks,Cars,Circuits,Trans,Engines,Tires,
Frames}[player][n]` with the high-score screen's `gPrevUnlocked*` copies, the race results (`gLap`, `gLapTimes`,
`gBestLapTime`, `gBattlePoints`, `gRankedPlayer`), the stunt players `gStuntPlayer[]` (MAT3 `tStuntPlayer`, 0x78:
`maxStuntPoints` +0x8, `totalPoints` +0x14, `totalStunts[10]` +0x48), the circuit (`tCircuit` in the save data,
`gCircuitCars[6]`, `gCircuitTracks[24]`, `gCircuitSeed`). A profile's save data (`tSaveData`) is MAT3's with every
offset from `raceStats` on 4 bytes lower.

**Option screens.** Each screen has its own statics: the 3-D buttons `buttonInfo[]` (MAT3 `tMenuButton`, 0x40:
type, object, angle +8, matrix +0xC with the position at +0x30, alpha +0x3C), `buttonsInited`, `validOption[]`,
the selected row, `gControllerRemoved` (the screen was opened because a controller came out), `menuRect`
{x, w, h, cx}, `panesCreated`, `titlePos`. The pause screen adds `pauseMenuSelect`, `gPauseState`, `pause_gYes`,
`pause_gPlayerRects` (where each player's rumble status goes).

**Targets** (`targets.c`). A target (`tTarget`, the same layout as MAT3) is a track object: `Flags` +0x4,
`dlIdx` +0xC (its zoid object), `infoIdx` +0x10, `mat` +0x14 (with the position at +0x38), `pos` +0x44, `frames`
+0x5A, `slot` +0x5C (the car that hit it), `owner` +0x65, `data` +0x6C (a type's own record: `tTargetStructCoin`,
the mine's, the velocity/rotation one). `targetInfo[]` (MAT3 `tTargetInfo`, 0x30 bytes on the N64) gives each type
its start and animate functions, its collision function (an index into the six `TargetColl*` functions) and its
sounds. A target's animation runs as an environment *visual* (`tVisual`: `data` is the target, `func` the
`Animate*` function, called with op 1 each frame and op 0 to release). The lists `gTargetList`, `gAlwaysColList`,
`gPlayerMines` (three mines per owner), the coin counters `gWhichGoldCoin`/`gWhichSilverCoin`.

**Interior symbols.** Several `D_` names point inside a bigger object: `best_lap_time_by_column` (=
`gBestLapTime` - 1, IDO folded a `[col - 1]`), `stunt_player_total_points` (= `gStuntPlayer[0].totalPoints`),
`target_info_start_sounds` (= `targetInfo[0].startSnd`), `gOptions_metric` (= `gOptions[9]`), `gText_single`
(= `gText.single`), `options_title_button_pos`, `video_title_button_pos`, `video_menu_center_x`, `hud_box_alpha`,
`gWprObjList_mine`/`gWprObjList_mine_glow` (= `gWprObjList[5]`/`[6]`), and part C's `audio_menuRect`'s and
`unitmatrix`'s inner ones. The map names them so the code reads, and says in each note which element or field
they are; wave 2 should replace them by that element or field.

## 5. How the functions call each other

**Start-up.** `main_thread_entry` (boot) calls `InitSystem`, which brings up the save system, graphics (`InitGraphics`:
`InitGfx`, `ZOID_Init`, `InitBlits`, `ZeroCameras`), audio, the controls (`InitRushControls`) and the text system
(`HAL_InitText`); the main thread then loops in `process_scheduler_message` for good: on a retrace it calls
`StartGraphics` (frame display lists, then `HAL_StartText`) and wakes the game thread; when the game thread
signals the frame done it calls `EndGraphics` (`HAL_FinishText`, closes the lists, posts the RSP task).

**Each frame.** `GameLoop` waits for the retrace or runs `UpdateFrame`; after 300 seconds without input it shows
the idle-warning blit (`idle_warning_multiblit`, animated by `animControllerDim`); then by game state:
`updateGameState`, `updateFrontEnd` on the front-end states (each screen's update, mostly in overlay A; the attract
race through `updateDemoGame`), the pause screen, or `UpdateGame` during a race. `UpdateGraphics` then runs
`DrawBlits` (every HUD and menu animator), `UpdateEnvirons` (the visuals, among them the targets' `Animate*`) and
`UpdateCameras`.

**A race.** `UpdateGame`: `CalcPolePositions`; `PrePlay` (`EnableGameSounds`, `InitCPS`, `init_cars` and
`munge_gLink_data`, `InitDrones`, `init_views` -> `init_view3` + `init_steady_move_cam`, `ShowHUD`, ...); the
countdown (`CarSetup`, `Update_MDrive`, `CountDown`, `CheckButtons`); the start (`CalcRaceTime`, `InitCPTime`); each
racing frame `PlayGame` (`DoDrones` -> `LinearInterp`; `CheckCPs` -> `FindMaxpathIntervals`, ...; the end-of-race
rules -> `FindWinner`); then `EndGame`, the high-score screen (`updateHighScoreScreen`: `highscore_InitScreen` ->
`RecordGameOver` -> `Record*`; `UpdateCircuit`, `CalcUnlockedStuff`, `RankScores`; per state `ControlUnlocked`,
`ControlName` -> `censor` -> `fixword`, `ControlGhost`) and the game-over menu (`updateGameOverScreen`).
`Update_MDrive` drives the model thread and calls `update_game_data` and `CheckCameraView` -> `update_camera` -> the
camera modes -> `point_at_car`.

**The HUD.** `ShowHUD` creates the HUD's multiblits at race start; every element is then an animator called by
`DrawBlits`. `hud_updateFrame` (an animator too) fills `TrackTimeStr` and `dot_order_list` for the others.

**The screens' drawing.** Each screen's overlay code installs a one-entry multiblit whose animator is the screen's
`animText` (`gameover_animText`, `highscore_animText`, `audio_animText`, `controls_animText`, `options_animText`,
`video_animText`); it calls the screen's `animButtonText` when the 3-D buttons are up and its draw helpers
(`drawMain`, `drawRect`, `DrawName` ...).

**Targets.** `CheckTargetCollision` (elsewhere) calls the target type's collision function from
`gTargetCollFuncPtrs` (`TargetCollBBox` ... `TargetColl3Piece`, order as in MAT3) and on a hit its start function
(`StartMine`, `StartCone`, ...), which grabs an environment visual whose function is the type's `Animate*`.

**MusyX.** The sound library calls its eight services through the table at `audio_driver_services` (filled by the data loader;
`port/main.c` checks it): submit the audio task and wait for it, set and clear the retrace callback the audio
thread calls (`musyx_retrace_callback`), start a sample DMA list (the DMA service in r1 walks the rest), turn a
sample offset into a cartridge address, allocate and free.

## 6. N64 only (no MAT3 counterpart)

- The frame pipeline: `StartGraphics`/`EndGraphics`'s bodies (RDP clears, split-screen bars, filter and dither
  options, the RSP task with rspboot and F3DEX2), `process_scheduler_message` and its handshake flags, the
  scheduler and thread queues, `ClearScreen`'s body, the text semaphore queue, `osTvType`.
- The audio manager's table functions (`stop_sequence`, `find_sequence`, `change_effect_*_pan`,

- The controller and rumble pak: `anim_no_rumble_panes`/`anim_no_rumble_text` (a pane and a line of text during
  the countdown for each player without a rumble pak), the pak records' rumble byte read by `animRumbleText`,

## 7. Not identified, least sure

Every function and datum has a name. The weakest:

1. The 13 empty stubs: their name is the function their position suggests, or just where they sit.
2. `anim_no_rumble_panes`, `anim_no_rumble_text`: N64-only HUD animators; the behaviour is clear, the text they
   show is a text-bank entry this page cannot read.
3. `animate_blit_unchanged` (returns 1, nothing else) and `noop_two_args`: no caller in the C.
4. `animate_pause_dim`: an animator like `animPause` without its `Hidden` test; which pause blit uses it is not
   visible in the C.
5. `animControllerDim`: MAT3's name by shape (44 bytes, as `pausescr.c`'s) and place (`game.c`'s data, where MAT3's
   `game.c` has an erased `animControllerDimInternal`); on the N64 it dims the screen for the idle warning.
6. `font_get_char_list`, `dot_uv_y_axis`, `find_closest_res_path_point`: no MAT3 twin and no caller.
7. `StartGraphics`/`EndGraphics`: MAT3's names of the GameCube platform calls, the same role, different bodies;

## 8. Things that look like bugs

All of them are the retail game's behaviour; keep them unless a setting says otherwise.

- `FindWinner` never resets the tie counters (`ties`, `tied[]`): MAT3 clears them first, the N64 doesn't and nothing
  else writes them, so ties of an earlier race in the session can reach the results text and `RecordBattle`'s wins.
- `CalcUnlockedStuff` (cheat branch, `CalcUnlockedStuff.c:299-300`) writes one row past the player data: with four
  players, past `gUnlockedCircuits[4][4]`.
- `FindTempNameIdx` (`FindTempNameIdx.c`) reads `best` uninitialised when no temporary name has an age.
- `ControlName` (`ControlName.c`) reads the byte before the name when the name is empty (as MAT3).
- `find_closest_res_path_point` (`find_closest_res_path_point.c:24`) returns an uninitialised index when no point is nearer
  than its start distance; nothing calls it.
- `updateBG` (`updateBG.c:94`) tests `y <= +(height << 5)` where MAT3 tests `<= -1`: almost every vertex
  votes +1 on y, so the background's y shift is rarely the unanimous -4 or +4 it should be.
- `anim_no_rumble_panes` keeps its panes in `resultPane[0..3]`, the handles `animResults` uses for the result
  panes. They run at different times (the countdown, the finish) and each removes its panes, so this is only a
  shared array, but a change to either must keep them apart.
- `update_car_object` indexes `FSCLS_from_one` (`FSCLS` - 1) by the frame scale: safe, but the label overlaps
  `camera_nextSwitch[3]`.
- Naming only: the audio screen's `Options` view swaps `gOptions[12]` (music volume) and `[13]` (effects volume)
  (`groups/audioscr/audio.c:29`); `setMiniFBCollisionForce.c`'s locals `behind`/`beside` are swapped relative to MAT3.
